# Changelog for Domain Manager

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

## [0.12.0] - 2026-07-28
### Added
- **Search options for the remaining registrar administrative-metadata fields on Domain** (ids 9417-9422): WHOIS privacy, transfer lock, domain lock, auto-renew and DNSSEC are now filterable/sortable bool fields, matching the fields already shown on the domain panel's "Registrar details" table. The Transfer/EPP auth code is filterable only via "is empty" — the raw value is never shown in search results or criteria, mirroring the panel's own "On file"/"Not on file" masking.
### Fixed
- **"Punycode name" search option matched every domain, not just IDN ones**: `name_ascii` was always populated from `IdnNormalizer::toAscii()`, which encodes a plain-ASCII domain to itself, so every non-IDN domain's cached value duplicated its real name and always matched, making the field useless as a filter. Now only genuinely distinct (real IDN) encodings are stored, with a one-time migration clearing the duplicate values already backfilled on existing installs.

## [0.11.9] - 2026-07-28
### Changed
- **Domain form panel: redesigned the domain identity header** (§9 Phase 17) — the Unicode domain name (19px/500, not a link) now carries a small "IDN" badge when a distinct Punycode form exists; the Punycode form itself renders on its own muted/monospace line with an icon-only copy-to-clipboard button (reusing GLPI 11 core's own `data-glpi-clipboard-text` delegated handler, no new JS); and two labelled outline buttons, "Visit" and "WHOIS" (linking to who.is), replace the previous plain side-by-side links. Pure-ASCII domains show only the name line. Also replaced the repeated "Not reported by this driver"/"Not on file" text in the Registrar details table with a muted em-dash carrying the same text as a tooltip, so populated values stand out more.
### Added
- **New `name_ascii` column on the plugin's state table**, caching each Domain's Punycode/ASCII form (`glpi_domains.name` stores the Unicode form, and MySQL has no IDN function) — backfilled for every existing Domain on upgrade and kept in sync going forward via a new `Domain` `item_add`/`item_update` hook (`HookHandler::domainSaved()`). Backs a new "Punycode name" search option (id 9416) on Domain, so pasting a Punycode string from a DNS log now finds the domain (previously only the native "Name" option existed, matching the Unicode form only).

## [0.10.1] - 2026-07-27
### Fixed
- **`Attempted to use invalid search options from itemtype: "Domain" with IDs 9403` warning still recurred after 0.10.0's `Installer::pruneStaleSearchOptionCriteria()`**: live testing confirmed `glpi_savedsearches`/`glpi_savedsearches_users` were already empty on the affected instance, so the stale reference wasn't a persisted saved search at all — `QueryBuilder::manageParams()` writes whatever criteria a request used back into `$_SESSION['glpisearch']` on every request (including its own first-touch default), a source no one-time DB migration can reach. Added `HookHandler::scrubStaleSearchSessionCriteria()` on `Hooks::POST_INIT` (fires on every page load, early enough to run before any `front/*.php` reads the session) to strip a stale `criteria`/`sort` reference to Supplier `9401` or Domain `9402`/`9403` from session on every request — a permanent, self-healing companion to the 0.10.0 migration, regardless of exactly which request first seeded the stale value into that session.

## [0.10.0] - 2026-07-27
### Added
- **Registrar (`suppliers_id`) is now lock-protected once a domain has a confirmed working registrar match** (Phase 14): previously this field had no server-side protection at all, only a read-only UI hint. A new "Unlink registrar" button/action (`DomainRegistrarUnlinkController`) clears it without requiring the unlock right, mirroring the existing "Reassign registrar" action's own narrower auth scope.
- **New Domain-level "Managed" search option** (Phase 14): filterable on the native Domains list, true whenever either role (Registrar or DNS) currently resolves to a real, active, driver-configured supplier — independent of whether the last sync attempt succeeded or errored. Mirrors the existing DomainRecord-level "Managed" field.

### Changed
- **DomainRecord field locking is now conditional per-sync, matching how Domain's own locking already worked**, instead of a fixed static field list — behavior-preserving today (every current DNS driver reports all four protected fields every time), but a future driver whose reported fields vary is now handled correctly without further plugin changes. See `ARCHITECTURE.md` §0.3/§9 Phase 14.
- **Search UI cleanup (addendum)**: dropped two dummy "Domain Manager" search options on Supplier/Domain (they only labeled `Log::history()`'s field column, cluttering the Search UI's generic "Plugins" category with no real filtering value — history entries now show a blank field and a `"[Domain Manager] "` message prefix instead) and one on Domain that duplicated a native option (`"Registrar (Financial information)"` — turned out core already exposes this via `Infocom::rawSearchOptionsToAdd()`'s search option id 53; an earlier verification pass had incorrectly concluded otherwise). The remaining real options (DomainRecord/Domain "Managed") now group under a "Domain Manager"-labeled category instead of falling into the unlabeled default. See `ARCHITECTURE.md` §3.7.1.

### Fixed
- **"Unknown column ...states_domains_id.is_managed" crash on the Domains list/search (Phase 15)**: the Phase 14 commit added the `is_managed` column migration and the Domain-level "Managed" search option in the same commit, but never bumped `PLUGIN_DOMAINMANAGER_VERSION`. GLPI only re-runs a plugin's `Migration` when the stored plugin version differs from the version constant, so on any instance already activated at 0.9.0, the new column's migration silently never ran — the search option then referenced a column that didn't yet exist on that instance. The join/table/field wiring itself (`glpi_plugin_domainmanager_states.is_managed`, `plugin_domainmanager_getAddSearchOptionsNew()`) was already correct and needed no change; this release's version bump is what actually triggers the pending migration to run on upgrade.
- **`Unknown column 'is_managed' in 'SET'` crash during the plugin upgrade itself (Phase 15, found immediately after the fix above)**: `Installer::addDomainManagedColumn()` queued the new column via `Migration::addField()`/`addKey()` (which only buffer the `ALTER TABLE`, executed once at the very end of `Installer::install()`), then immediately ran a raw, unbuffered `$DB->update()` backfill loop against that same column — before the queued `ALTER TABLE` had actually run. Only manifests on upgrade of an existing install (where the backfill loop's `!$column_existed` branch actually executes); a fresh install never hits it because `createTables()`'s raw `CREATE TABLE` already includes the column. Fixed by calling `$migration->executeMigration()` immediately after queuing the field/key, flushing the schema change before the backfill queries run.
- **`Attempted to use invalid search options from itemtype: "Domain" with IDs 9403` warning on the Domain list (Phase 15, found after the upgrade fix above)**: a saved search/bookmark created before the Phase 14 addendum's Search UI cleanup still referenced the dropped dummy option id `9403` (or `9401`/`9402`) by number; GLPI's `QueryBuilder::validateFilters()` already silently drops an invalid criterion at render time, but re-triggers this warning on every subsequent render since nothing ever rewrote the saved search itself. `Installer::pruneStaleSearchOptionCriteria()` (new, runs on every install/upgrade) rewrites any `glpi_savedsearches` row for `Domain`/`Supplier` still carrying one of these three retired IDs, stripping just that criterion and leaving the rest of the saved search intact. A per-session "last search" for Domain/Supplier (not DB-persisted) may still show the warning once until the next fresh search or re-login — this is expected and self-resolving.

## [0.9.0] - 2026-07-27
### Changed
- **"Domain type to apply to imported domains" is now a configurable setting instead of hardcoded (Phase 12)**: a new "Domain Manager" tab on Setup > General (`plugins/domainmanager/Config`, `GlpiPlugin\Domainmanager\Config\Config`, stored via GLPI's native config store under the `plugin:domainmanager` context — no new table) lets an admin pick which native `DomainType` (if any) gets applied to a domain the plugin creates via bulk import (Phase 8). Left empty (the default for a fresh install), imported domains get no type at all, exactly like one created by hand — the plugin never sets or revisits `Type` again afterward on any later sync, since it's a purely local GLPI classification never sourced from any registrar/DNS API. An existing install upgrading from a pre-0.9.0 version has this setting defaulted automatically to the previously-hardcoded "Internet Domain" type at migration time, so upgrading changes nothing about current behavior until an admin deliberately changes the setting. `Type` remains deliberately excluded from the plugin's locked-fields list — it always was, and this change doesn't alter that: the setting only affects the one-time value at creation, an admin is always free to change it afterward. See `ARCHITECTURE.md` §6.6/§9 Phase 12.

### Fixed
- **Found while adding Strato/Arsys above: the IONOS registry entry's `*.ui-dns.{de,com,org,biz}` patterns were a bare domain-wide wildcard, silently matching every sibling United Internet brand's nameservers on the same shared `ui-dns.*` platform** — not just Strato/Arsys, but also 1&1 (`ns-1and1.ui-dns.*`) and Fasthosts (`ns-fh.ui-dns.*`), confirmed live via `dig NS` against each brand's own domain. ## [0.6.0] - 2026-07-27
### Added
- **NS detection for bunny.net (Bunny DNS)**: added `kiki.bunny.net`/`coco.bunny.net` to `resources/ns-providers.json`, confirmed against bunny.net's own docs (https://docs.bunny.net/dns/nameservers). Detection-only, no driver — bunny.net is a CDN/DNS host, not a domain registrar.
- **Bulk-import discovery for Dinahosting registrar accounts (Phase 8 addendum)**: the "Import Domains" button on the Supplier tab now also appears for Dinahosting suppliers, not just IONOS. Dinahosting's `Services_GetDomains` command returns every domain on the account in one flat, unpaginated call, including its real expiration date — shown as a preview hint next to domains not yet in GLPI. See ARCHITECTURE.md §9 Phase 8.
- **Bulk-import discovery for Cloudflare registrar accounts (Phase 8 addendum)**: the "Import Domains" button now also appears for Cloudflare suppliers. Uses Cloudflare's newer, cursor-paginated `/registrar/registrations` list endpoint, including each domain's real expiration date as a preview hint. See ARCHITECTURE.md §9 Phase 8 and §3.12.
- **IDN / Punycode handling (Phase 10)**: internationalized domain names (e.g. `viñamoraima.com`) were silently broken across NS detection, registrar sync, and DNS sync, since DNS itself and every driver's API only operate on a domain's ASCII-compatible Punycode (`xn--...`) form, not the human-readable Unicode form GLPI stores as `Domain::name`. A new `IdnNormalizer` service (wrapping the `intl` extension's `idn_to_ascii()`/`idn_to_utf8()`, modern UTS46/nontransitional mode) is now the single conversion point, wired into the NS lookup and every driver's outbound domain-name handling, plus response-side normalization (IONOS's zone/domain-id lookups, the Phase 8 bulk-import existence check) so a provider echoing a name back in the other form can't be misread as "not found"/"doesn't exist yet." `intl` is now a hard, activation-blocking dependency. The Domain Manager panel gains a read-only "Punycode / ASCII form" field, shown only for domains where it actually differs from the stored name. See ARCHITECTURE.md §3.11.
- **IONOS registrar domain lookup no longer relies on the Domains API's `name` filter (Phase 10 addendum)**: live testing against a real IONOS account found neither encoding of that filter works for an IDN domain like `viñamoraima.com` — Punycode returns a clean but wrong "No IONOS domain item found," while querying with the literal Unicode form gets rejected outright by IONOS's own gateway (a raw HTML `400 Bad request`, not their normal JSON error). `IonosDriver::findDomainId()` now skips the filter and matches the full unfiltered domain list client-side instead, the same pagination approach already used for Phase 8's account listing. The DNS zone lookup is unaffected (it never used a server-side name filter). See ARCHITECTURE.md §3.11.
- **Registrar reassignment now shows a distinct "Registrar changed, not yet verified" badge (Phase 8 addendum)**, on both the Domain form panel and the Supplier's "Domains" list, instead of silently continuing to show the *previous* registrar's last sync result (e.g. a stale "OK") right next to the newly-assigned supplier's name. The badge clears automatically the next time that domain is synced. See ARCHITECTURE.md §9 Phase 8.

### Changed
- **`CloudflareDriver` migrated off the deprecated Registrar Domains API (`/registrar/domains`, `/registrar/domains/{domain}`) to the newer Registrations API (`/registrar/registrations`, `/registrar/registrations/{domain}`)**, confirmed against Cloudflare's current live OpenAPI spec that the old endpoints are marked `deprecated: true` with an EOL of 2026-09-27. This affects both `fetchLifecycle()` and the new bulk-import discovery above. The new schema isn't a pure rename: `registry_statuses` (free-text list, previously substring-matched for "hold") is replaced by an explicit `status` enum (`active`/`registration_pending`/`expired`/`suspended`/`redemption_period`/`pending_delete`, mapped directly rather than guessed), and `privacy` (plain bool) is replaced by `privacy_mode` (`false`/`"redaction"`), normalized to the same bool-or-null shape. No other registrar-detail fields changed. See ARCHITECTURE.md §3.12.
- **"Update Now" moved from the Domain form's "Domain Manager" ribbon-banner header down into the same button row as "Put in trashbin" and "Save"**, styled the same way (`btn btn-outline-secondary`, same size/padding/border as its neighbours) instead of the smaller, separately-styled corner button it used to be. Purely a placement/style change — the button's function (triggering an immediate sync) is unchanged. See ARCHITECTURE.md §9 Phase 9 addendum for why this required a small client-side relocation script rather than a template-level fix.
- **The Supplier tab's "Domains" list now shows an Entity column**, using GLPI's own tree/breadcrumb entity badge (the same convention core itself uses for a read-only Entity field elsewhere) — so which entity a listed domain belongs to no longer requires opening it individually, useful now that this instance is multi-entity and Phase 8 lets domains be imported into a chosen entity. See ARCHITECTURE.md §9 Phase 9 addendum.

## [0.5.0] - 2026-07-22
### Added
- **Bulk-import undiscovered IONOS registrar domains (Phase 8, IONOS slice)**: an "Import Domains" button on the Supplier tab (shown only for suppliers whose configured driver actually supports it — IONOS today) opens a modal listing every domain in that registrar account, checked against GLPI's own inventory (global, cross-entity, case-insensitive/trimmed). Domains not yet in GLPI are checked by default and ready to import in one batch into a chosen entity; domains that already exist are shown read-only, flagged "Registrar mismatch" with a one-click "Reassign/Set registrar to X" fix when their stored registrar disagrees with this account. Imported domains get their registrar link and an initial sync applied immediately, so they don't sit at "Not yet checked." No database migration is needed for this phase — nothing discovered here is persisted until it's actually imported. See ARCHITECTURE.md §9 Phase 8 for the full design, including what's deliberately deferred (Cloudflare/Dinahosting discovery, the Domain form's own "Registrar mismatch" surface, and NS-provider registry additions).
- **Richer registrar domain metadata (Phase 7a)**: the Domain form's "Domain Manager" panel now shows a "Registrar details" section (WHOIS privacy, domain lock, transfer lock, auto-renew, DNSSEC, domain type, and whether a transfer/EPP auth code is on file) once a domain's registrar sync succeeds. IONOS's registrar API can report all 7 fields; Cloudflare reports 3 of them (WHOIS privacy, transfer lock, auto-renew — confirmed live against its current API spec); Dinahosting reports 1 (the auth code, via a real command whose response shape was safely inferred from two already-trusted sibling commands) — every other per-driver gap is a confirmed, spec-verified structural absence or an explicitly flagged pending-live-verification case, never a guess. The EPP/transfer auth code itself is persisted but deliberately never displayed in the UI — it's a transfer-enabling secret, and the panel only shows whether one is on file. Verified live end-to-end against both a real IONOS-registered and a real Dinahosting-registered domain. See ARCHITECTURE.md §9 Phase 7a for the full per-driver support matrix and reasoning.
- **Searchable "Proxy status" field on Domain Records (Phase 7b)**: a new, real, filterable search option showing whether a Cloudflare-managed DNS record is CDN-proxied (Yes), DNS-only but proxy-eligible (No), or not applicable (blank — any non-Cloudflare record, or a Cloudflare record type/state Cloudflare itself reports as non-proxyable via its own live `proxiable` flag, checked per-record rather than assumed from a hardcoded type list). "Yes"/"No" filtering is exact; filtering by "is empty" is a documented, GLPI-core-level limitation for `bool`-typed search options in general (it matches "No" together with "not applicable," not "not applicable" alone) — see ARCHITECTURE.md §9 Phase 7 addendum for the confirmed root cause and why this plugin can't override it for a core itemtype. Verified live end-to-end (real search-engine round trip against real test data, including the underlying SQL) rather than assumed from the search option's declared datatype.

### Fixed
- **Found and fixed while implementing Phase 7a**: a native PHP `true`/`false` passed into a `CommonDBTM::update()`/`add()` input array is silently persisted as `NULL` instead of `1`/`0` — caught live when a real sync's in-memory result held `true` for two fields that ended up `NULL` in the database. Every nullable boolean-ish column this plugin writes now goes through an explicit `int`/`null` cast before reaching an update/add call, matching the `1`/`0` convention this codebase's *existing* tinyint columns (`is_active`, `is_managed`) already happened to follow. See ARCHITECTURE.md §0.10 — directly relevant to Phase 7b's planned `is_proxied` tri-state column.

## [0.4.0] - 2026-07-21
### Fixed
- **The API driver dropdown on a Supplier's Domain Manager tab could assign the same driver (Cloudflare/IONOS/Dinahosting) to more than one supplier**, leaving it ambiguous which supplier's credentials the sync engine should use for that driver. A driver already claimed by a different supplier is now excluded from the dropdown (the current supplier's own already-saved driver always remains selectable/selected), and the same rule is enforced server-side in `SupplierConfig::prepareDriverAndCredentials()` so a direct POST bypassing the dropdown is rejected too, with a clear error message. No bulk-edit path exists for this field today (`SupplierConfig` has no search/list page; the existing "Sync now" massive action only syncs domains), so there was no batch path to guard.
- The driver dropdown now sorts alphabetically by display label ("Cloudflare", "Dinahosting", "IONOS"), with "None" always pinned first, instead of its previous unordered (registration-order) listing.
- **Supplier tab's "Domains" list undercounted registrar-linked domains** — reported as "Supplier's native Items tab shows 3, the Domains panel shows 1 for the same supplier," confirmed live. The query only ever `INNER JOIN`ed the plugin's own state table, so a domain was invisible until a sync/detection had already produced a state row — even though its registrar link (via `glpi_infocoms.suppliers_id`, the same native link behind the Items tab count) was already real and immediately knowable, no sync required. Fixed to read that link live via a `LEFT JOIN`, unioned with the existing DNS-side condition; an existing GLPI instance with domains already assigned to suppliers now sees them correctly immediately after installing this plugin, with no cron cycle required. `registrar_status` now only comes from a state row when that row's own registrar mirror actually agrees with the live Infocom value — otherwise it honestly shows "Not yet checked" rather than a stale, possibly-wrong status.
- **`SyncEngine` never actually resolved the registrar from Infocom, only from a state-row mirror that could go stale** — found while fixing the above (same root cause): a domain whose Infocom registrar assignment predated or otherwise missed the mirror-sync hook stayed permanently "unconfigured" no matter how many times it was synced. `sync()` now reads Infocom live and self-corrects the mirror on every run, so "run a sync" (the new recommendation banner and massive action below) actually resolves what it's flagging, not just cosmetically.
- **An inactive supplier's stored credentials could still be used for connection tests, syncs, and cron** — nothing checked the native "Active" field before an outbound API call. `SupplierConfig::isSupplierActive()` now gates every one of those call sites (`SyncEngine`'s registrar/DNS legs, `ConnectionTestController`, and transitively cron + the "Sync now" massive action, since both just call `SyncEngine::sync()`): an inactive supplier's credentials are never decrypted or sent, the leg reports a new, distinct `supplier_inactive` status instead of a generic error, and the skip is logged to `domainmanager.log` only (never `-errors.log`, since it isn't a failure, and never the domain's Historical tab, since a no-op repeating on every cron run isn't a milestone).
- **Dinahosting misreported "authentication failed, check the username/password" for a domain that isn't authorized under the configured account, even when the credentials themselves are demonstrably correct** — reported live: domain `pontecm.com` showed registrar = auth-failed while a different domain (`tic.gal`) under the exact same supplier/credentials synced fine and Check Connection reported success. Root cause: `DinahostingDriver::request()` collapsed response codes `2200` (real credential rejection) and `2201` (credentials valid, but this specific domain isn't authorized for the account) into one identical message, even though the connection-test code path already correctly treated them as distinct outcomes. `2201` now gets its own accurate message ("...this account is not authorized to manage this domain") instead of wrongly implying the username/password is wrong.

### Changed
- **Cloudflare now requires an "Account ID" alongside the API Token, and only supports an Account API Token** (Manage Account → API Tokens) — a personal/user token (My Profile → API Tokens) is not supported and will fail authentication here, even if otherwise perfectly valid: it's tied to whoever created it and breaks if that person loses access, whereas an account token belongs to the Cloudflare Account itself. The zone lookup is now correctly scoped to the configured account (`account.id` query filter, confirmed against Cloudflare's current live API spec) instead of trusting the first name match across whatever the token can see, and the registrar lookup uses the stored Account ID directly instead of depending on a DNS zone existing first. New help text on the Supplier tab explains where to create the right kind of token and find the Account ID. Existing Cloudflare configs saved before this change (token but no Account ID) show a clear warning notice on the Supplier tab instead of silently breaking or silently continuing on the old, less-scoped behavior; `Check Connection` reports a distinct "Not configured" status for a missing Account ID, never conflated with an actual authentication failure. No database migration needed — the Account ID is stored in the same encrypted credentials JSON as the token, like every other driver's credential fields.
  - **Caught during testing: a genuinely valid, freshly created Account API Token still failed Check Connection with "Authentication failed"/HTTP 401.** Root cause: `probeTokenVerify()` still called `user/tokens/verify`, which structurally rejects account-owned tokens regardless of validity — confirmed against Cloudflare's live API spec that `user/tokens/verify` and `accounts/{account_id}/tokens/verify` are two distinct endpoints, and independently confirmed as a known quirk other integrators have hit too. Fixed by verifying against the account-scoped endpoint using the same Account ID already required for the zone/registrar lookups.
- **A DNS record that disappears from the upstream zone is now moved to GLPI's native trash bin (`is_deleted = 1`, restorable) instead of being flagged with a plugin-invented comment marker** — replaces the earlier "flagged removed, never deleted" design entirely. If the record reappears in a later sync, it's restored from the trash bin natively (`DomainRecord::restore()`), never re-created as a duplicate. The plugin's own `is_stale` tracking column is gone (migrated away, with existing rows automatically reconciled); "was this stale" is now read directly from the native `is_deleted` field, removing a second plugin-owned flag that could drift out of sync with it. The existing sync-in-progress lock bypass already covers this soft-delete/restore for free — no new lock-enforcement code was needed. Verified live against a real GLPI instance: trash, restore, and re-sync all behave correctly with no duplication.

## [0.3.2] - 2026-07-21
### Fixed
- **Critical: any connection test silently wiped the supplier's stored API credentials, one click after they were saved.** Reported as "credentials get deleted every time we disable or upgrade the plugin" — reproduced live and traced to a different, more specific trigger: `SupplierConfig::prepareInputForUpdate()` (a `CommonDBTM` hook that fires on **every** `update()` call for this itemtype, not just the credentials-save form) unconditionally re-derived `api_driver`/`api_credentials` from its `$input`. `ConnectionTestController::recordConnectionTestResults()` calls `update()` with only the `*_test_*` columns — no `api_driver` key at all — so `$input['api_driver'] ?? Net effect: the first Check Connection (or any sync) after a save succeeded correctly against the live API; persisting that very success/failure result wiped the credentials, so the *next* attempt failed with "API key/secret are not configured" — which likely read as data loss correlated with whatever the admin did around that time (a deactivate/reactivate cycle followed by a verification click, in the original report). Fixed by only touching driver/credentials when `api_driver` is actually present in the input — any other partial update now leaves them untouched. Verified live: credentials now survive repeated Check Connection calls, real syncs, and both same-driver empty-submit saves and legitimate driver switches still behave exactly as before.
- `glpi_plugin_domainmanager_supplierconfigs.api_credentials` is now registered via `Hooks::SECURED_FIELDS`, found while investigating the above (a separate, narrower gap): without this, a core-wide `security:change_key` key rotation would silently skip re-encrypting this field, permanently orphaning every stored credential under the old, discarded key.
